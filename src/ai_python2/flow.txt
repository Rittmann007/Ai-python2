ingest:
takes the input data
|
chunks the input
|
embeds every chunk
|
stores the embedding with the corresponding input data and interviewID,sourceType(for filtering)

chat:
takes the query
|
llm sees the query and decides which tool to call, now the tool either web search or
    |
    embeds the query
    |
    matches with the other embeddings in the db filtered by interviewID and sourceType
    |
    takes out the matching data
    |
puts it in context along with query
|
gives to the llm, returns the result

ℹ️we could make one tool for context search without making separate tool for each input context, but
- when get_query_results runs $vectorSearch filtered on interviewID, 
the filter is working correctly — that's why every chunk you saw belonged to the same interview. 
But within that one interview's chunks, the top-k similarity search freely mixes in JD text 
("Location: Remote / Hybrid" — that's from this interview's own job posting, not another candidate)
 and self-description text ("I am a detail-oriented software developer..." — from this interview's self-description).
  For a query like "where do I work," a JD line like "Frontend Developer... 
  Remote/Hybrid" can easily out-rank the actual resume's employer line, 
  because nothing tells the vector search "only look at resume chunks."
