Your project is meant to be installable as a package, 
and package code is kept under src so the import path matches what gets installed. 
That reduces accidental imports from the working directory and 
makes local development behave more like a real install.
This style is common for projects that may grow beyond a one-file script.
It separates the packaging surface from your notebooks, experiments,
and other root-level files, and it avoids the import confusion 
that flat layouts often create.


ℹ️ why need to run the virtual environment to work on the project?
- Because this project has its own Python environment, and that environment contains the packages declared in pyproject.toml.

When you run:   .venv\Scripts\activate

you are telling your shell:
use the Python inside this project’s virtual environment
use the packages installed there
keep that environment separate from your system Python
Without activating it, your terminal may still use a different Python interpreter, and then:

fastapi may not be found
langchain may not be found
python version may be wrong

It isolates dependencies per project.

Think of the virtual environment as:

your project’s personal Python installation
separate from the machine-wide Python
with exactly the libraries this project needs

ℹ️ whats the difference between @app.post and app.post?
- @app.post("/x") is a decorator syntax.
app.post("/x") is a direct method call.

@app.post(...) is the usual, cleaner FastAPI style
app.post(...) works too, but you must pass the function object afterward
